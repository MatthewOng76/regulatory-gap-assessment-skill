A reusable skill for structured regulatory gap analysis.

A public skill for line-by-line regulatory assessment in Excel, designed to preserve verbatim regulatory text, cumulative internal evidence, append-only reassessment history, and outputs that remain usable for review, filtering, and pivot analysis.

What it does

Turns regulatory assessment into a repeatable evidence workflow.

The skill processes regulations sequentially, splits compound passages into atomic requirements, preserves the exact wording that matters, and then tests internal policy evidence against each requirement without guessing from topical similarity.

  • Every claimed match requires verbatim internal evidence
  • Multiple internal standards can collectively satisfy one requirement
  • New evidence can strengthen, weaken, contradict, or overturn earlier conclusions
  • Reassessment history is preserved instead of overwritten
Why it matters

Change the model if you want. Keep the machine: method, evidence discipline, structure, and output logic.

This skill is meant for teams who need a more defensible way to assess regulations against internal standards — especially where exact wording, cumulative evidence, and auditability matter more than fast summaries.

AudienceRisk, compliance, governance, controls, and internal standards teams.
Use caseMap regulatory requirements against internal policy evidence without collapsing everything into one opaque narrative cell.
Output shapeOne row per requirement × version × internal evidence source, with repeated conclusions where Excel usability needs them.
How to use it

Two simple prompts are enough.

This example is intentionally framed around Microsoft Co-pilot in an organisation, working inside an already-open Excel workbook, because many teams may not have premium access to more advanced internal AI agent setups. The instruction file should carry the methodology, so you should not need to restate it in detail to Co-pilot. Have Co-pilot work with the open Excel workbook, the Markdown instruction file, and the relevant source documents in the same active context, then use one prompt to start the analysis and one prompt whenever you add another internal standard.

Starting a new analysis

Open the workbook you want Co-pilot to populate, then use:

Use the instruction file to perform a complete regulatory gap analysis in this open workbook. Follow the instructions in the file exactly. Ask me for the Regulation paper and internal policy/standard document 1 if you do not already have them. Continue through the full analysis and validation.

Co-pilot should then ask for the first source documents. For example:

  • Regulation paper
  • Internal policy/standard document 1

It should produce just Summary and Detailed_Analysis, with the regulatory side atomically decomposed and the first internal standard mapped against it.

Adding another internal standard later

Do not ask it to perform another gap analysis. Ask it to extend the existing one:

Using the instruction file, incorporate internal policy/standard document 2 into the existing analysis in this workbook. Do not restart the analysis or recreate the regulatory requirements. Preserve all existing Requirement IDs and verbatim regulatory quotations. Identify which existing requirements this additional standard could materially affect, add its verbatim internal evidence, and reassess those requirements holistically together with all previously reviewed internal standards. Update both Detailed_Analysis and Summary, including any changed gaps, collective coverage, internal inconsistencies and recommendations.

Once Co-pilot follows the Markdown reliably, the prompt can be shortened:

Using the instruction file, add internal policy/standard document 2 to the existing analysis and perform the incremental cross-standard reassessment. Preserve the existing regulatory decomposition and Requirement IDs.

Then later:

Using the instruction file, add internal policy/standard document 3 to the existing analysis and perform the incremental cross-standard reassessment.
Implement it as a Skill.md file

Keep the method in the file, not in the prompt.

If you want to operationalise this beyond a single workbook session, package it as a Skill.md file with a small, predictable folder structure. The naming should be boring and explicit so both people and agents can find it quickly.

Example file and folder structure

regulatory-gap-assessment/ ├─ Skill.md ├─ templates/ │ ├─ workbook-template.xlsx │ └─ summary-template.md ├─ examples/ │ ├─ prompt-start-new-analysis.txt │ └─ prompt-add-internal-standard.txt └─ docs/ └─ implementation-notes.md

Naming convention

  • Skill.md for the main instruction file
  • Use lowercase, hyphenated folder names for the skill package
  • Keep examples and templates in clearly named subfolders
  • Name prompts by purpose, not by version history

Example execution patterns

You can execute the same method in several ways depending on the environment available to you:

CLI example agent run ./regulatory-gap-assessment/Skill.md \ --workbook ./workbooks/current-analysis.xlsx \ --regulation "Regulation paper" \ --internal-doc "internal policy/standard document 1"
API example POST /v1/skills/execute { "skill": "regulatory-gap-assessment/Skill.md", "workbook": "current-analysis.xlsx", "inputs": { "regulation": "Regulation paper", "internal_documents": [ "internal policy/standard document 1", "internal policy/standard document 2" ] } }
Agent example Use Skill.md in regulatory-gap-assessment to continue the analysis in the open workbook. Preserve existing Requirement IDs, keep the regulatory decomposition unchanged, and incorporate internal policy/standard document 2 into the existing assessment.

The common pattern is the same: the Skill.md file holds the durable methodology, while the call only supplies the workbook context and the current source documents.
